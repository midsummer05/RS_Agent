# 遥感影像解译 Agent：分阶段开发文档

## 1. 项目定位

本项目是一个面向遥感影像解译的 Agent 工程样例，而非遥感算法精度竞赛。它要证明的是：面对大文件、多工具、长耗时任务和不确定性，系统能够稳定编排、保存状态、解释决策、接受人工干预，并在失败后恢复。

### 1.1 MVP 边界

第一版仅支持两种影像来源和两个明确任务：

| 影像类型 | 示例数据 | 支持任务 | 基线工具链 |
| --- | --- | --- | --- |
| 光学 RGB/多光谱 GeoTIFF | 航片或 Sentinel-2 切片 | 水体、建筑物提取 | NDWI/颜色指数或预训练轻量分割模型 + 形态学后处理 |
| SAR GeoTIFF | Sentinel-1 切片 | 水体提取 | 去斑 + 自适应阈值 + 形态学后处理 |

首期不承诺任意传感器、任意地物或生产级精度。不同分辨率的支持指：系统读取分辨率与坐标参考，根据工具约束选择重采样、切片和参数策略，并以真实地理面积而非像素数量进行统计。

### 1.2 非目标

- 不训练模型，也不把原始影像输入 LLM 上下文。
- 不做在线遥感数据下载平台、复杂账户系统或分布式集群。
- 不以 SOTA 语义分割精度为验收重点。
- 不配置 GDAL CLI、完整驱动集或复杂的系统级地理空间运行环境。

## 2. 总体架构

宏观工作流固定，微观决策受 LLM 驱动：

```text
任务请求
  │
  ▼
[影像数据预处理] → [核心解译] → [结果后处理] → [指标统计与质检] → [报告生成]
       │                │               │                 │               │
       └──── 每阶段：规划 → 工具执行 → 产物落库 → checkpoint ────┘
                         │
                         └── 失败重试 / 回退方案 / 人工审批
```

### 2.1 控制流与数据流分离

- **控制流**：状态机、阶段路由、LLM 规划、人工审批、重试与 checkpoint。
- **数据流**：影像、切片、掩膜、矢量和报告文件经 Artifact Store 的 URI 传递。
- **LLM 上下文**：只包含结构化摘要，例如影像元数据、质量指标、工具清单、产物 URI、当前阶段、失败原因和历史决策摘要。

### 2.2 核心模块

| 模块 | 职责 |
| --- | --- |
| Orchestrator | 固定状态机与阶段进入/退出条件；执行恢复与路由。 |
| Planner | LLM 输出符合 JSON Schema 的受约束计划：工具、参数、理由、回退策略。 |
| Tool Registry | 登记工具的输入输出契约、适用影像类型、分辨率限制、版本、重试策略。 |
| Artifact Store | 保存不可变的中间和最终产物，并记录校验值与溯源。 |
| State / Checkpoint Store | 保存任务、阶段、计划、执行记录、审批和产物引用。 |
| Trace Store | 保存每次模型决策、工具调用、耗时、错误和状态迁移。 |
| Evaluation Harness | 批量运行案例，输出任务效果与 Agent 工程指标。 |

### 2.5 Web 呈现与容器化后端

项目以 **Web 端** 作为唯一的用户交互入口，展示任务创建、影像元数据、阶段状态、人工审批、结果预览、统计报告和 trace 回放。前端不直接读取影像原始文件，也不直接持有任何模型或 API 密钥。

所有后端运行单元必须通过 Docker 构建，并使用 Docker Compose 以同一份配置启动。推荐的最小部署拓扑如下：

```text
Browser Web UI
      │ HTTPS / REST / SSE
      ▼
API Service (Docker) ─────── Shared state volume
      │                         ▲
      │ enqueue / query          │ checkpoints, approval, trace
      ▼                         │
Worker Service (Docker) ─── Artifact volume
      │
      └── DeepSeek API（仅由 Worker/Planner 经服务端环境变量调用）
```

| 服务 | 容器职责 | 是否对浏览器公开 |
| --- | --- | --- |
| `web` | Web UI 静态资源与任务可视化 | 是 |
| `api` | 任务 API、审批 API、产物授权访问、SSE 状态推送 | 是 |
| `worker` | 状态机、Planner、影像工具、重试和报告生成 | 否 |
| `state` | 共享 SQLite 文件卷（MVP）；后续可替换为独立 PostgreSQL 容器 | 否 |
| `artifact` | 本地挂载 volume（MVP）；后续可替换为兼容对象存储 | 否 |

MVP 可以让 `api` 与 `worker` 使用同一个 Python 镜像、不同启动命令；这能降低镜像维护成本，同时保持 API 服务与长耗时任务隔离。影像、数据库和 trace 均使用命名 volume 或宿主机映射目录持久化，重建容器不会丢失 checkpoint。`.env` 只在 Compose 启动时注入服务端容器，绝不打入镜像或暴露给 `web` 容器。

### 2.3 轻量影像适配策略

第一版不直接使用 GDAL 的 Python 绑定或命令行工具。实现一个 `ImageAdapter` 接口，只覆盖本项目需要的 2--3 类输入：普通 PNG/JPEG、带地理参考的光学 GeoTIFF、SAR GeoTIFF。优先选择安装和调用成本较低的库：

| 能力 | 首选实现 | 备注 |
| --- | --- | --- |
| PNG/JPEG、普通 TIFF 读写 | Pillow / tifffile | 面向像素级处理和演示。 |
| GeoTIFF 元数据、窗口读取、基础重投影 | Rasterio 的有限 API | 仅安装 Python wheel，不配置 GDAL CLI、额外驱动或全量系统环境；底层依赖由 wheel 管理。 |
| 数组、滤波与形态学 | NumPy / OpenCV / scikit-image | 用于轻量处理算法。 |

如果部署环境无法使用 Rasterio wheel，则将 GeoTIFF 限制为已对齐、带标准 EPSG/仿射变换的样例，并用 `tifffile` 读取像素、从 manifest 提供地理参考。这样会牺牲通用地理坐标处理能力，但不影响 Agent 工程演示。

### 2.4 LLM 接入与密钥管理

项目的 Planner 默认接入 **DeepSeek V4 Pro**。应用层不得依赖具体厂商：通过 `LLMClient` 抽象调用规划模型，便于在离线测试中替换为 mock client，或在需要时替换模型提供商。

| 配置项 | 用途 | 存放方式 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | DeepSeek API 密钥 | 仅本机环境变量或未提交的 `.env` 文件 |
| `DEEPSEEK_MODEL` | 模型标识 | 本机环境变量；值采用 DeepSeek 官方 API 当前要求的 V4 Pro 标识 |
| `DEEPSEEK_BASE_URL` | API 地址 | 可选本机环境变量 |

**严禁**将真实 API 密钥写入 Markdown、源代码、测试夹具、日志、trace、checkpoint、数据 manifest 或 Git 历史。`.env` 必须被 `.gitignore` 忽略；仓库只提供不含密钥的 `.env.example`。日志中仅记录模型名称、请求耗时、token/费用摘要（如可得）和请求 ID，禁止记录鉴权头或完整密钥。

PowerShell 本机配置示例：

```powershell
$env:DEEPSEEK_API_KEY = "在此处粘贴本机密钥"
$env:DEEPSEEK_MODEL = "填写 DeepSeek API 当前的 V4 Pro 模型标识"
```

如密钥曾出现在聊天记录、终端输出或已提交文件中，应立即在提供商控制台轮换，并删除旧密钥；轮换后只在本机安全存储中更新。

## 3. 状态、checkpoint 与重试设计

### 3.1 最小任务状态

```json
{
  "job_id": "uuid",
  "status": "running|waiting_human|failed|completed",
  "stage": "preprocess|interpret|postprocess|qa|report",
  "request": {"task_type": "water_extraction"},
  "image_manifest": {"uri": "artifacts/...", "sensor_type": "optical"},
  "artifacts": [],
  "plan": {"version": 1, "tool": "...", "parameters": {}},
  "attempts": [],
  "quality": {},
  "approval": null,
  "memory_refs": []
}
```

### 3.2 checkpoint 规则

1. 工具产物先持久化，再写 checkpoint；状态只保存 URI、哈希和摘要，不保存影像数组。
2. 每次阶段完成、人工中断、可恢复错误和最终完成都创建 checkpoint。
3. 工具调用必须携带 `job_id`、`step_id` 和幂等键；恢复时优先复用已存在且哈希一致的产物。
4. checkpoint 可回放，允许从任一成功阶段重新规划后续路径。

### 3.3 失败策略

| 失败类型 | 自动动作 | 是否人工介入 |
| --- | --- | --- |
| 瞬态错误（超时、临时 I/O） | 指数退避重试，最多 2 次 | 否 |
| 参数/工具不兼容 | 将错误摘要交给 Planner，换参数或回退工具 | 否 |
| 影像质量差或质检不通过 | 生成候选处理方案 | 是 |
| 数据缺失、坐标系无法确定 | 暂停任务 | 是 |
| 报告发布 | 低置信度或高风险结果需审批 | 可配置 |

人工操作固定为 `approve`、`edit`、`reject` 三种，并完整记录到 trace。

## 4. 分阶段实施计划

## Phase 0：工程骨架与契约（第 1 周）

**目标**：跑通不含 LLM 的固定工作流与可恢复状态机。

- 初始化 Python 项目、配置、日志、格式化和测试框架。
- 初始化 Web 前端、后端 API、worker 的目录骨架，以及 Dockerfile 和 `compose.yaml`；所有后端服务必须可由 Compose 启动。
- 定义 Pydantic 数据模型：任务、产物、工具契约、执行计划、质量结果、审批事件。
- 实现本地 Artifact Store 与 SQLite State Store。
- 实现五阶段状态机、阶段转换校验、checkpoint 与恢复命令。
- 用 mock 工具生成假掩膜和假统计，覆盖成功、失败、恢复三条路径。

**验收标准**：`docker compose up` 可启动 Web、API 与 worker；worker 在核心解译阶段被中断后重启，可从最近成功 checkpoint 恢复，且已完成的 mock 工具不重复运行。

## Phase 1：遥感 I/O 与确定性工具（第 2 周）

**目标**：让真实影像走完整个无 LLM 流程。

- 实现轻量 `ImageAdapter`：处理 PNG/JPEG、光学 GeoTIFF 与 SAR GeoTIFF；完成影像检查、元数据读取、基础重采样和切片。
- 仅在样例确有坐标系不一致时使用 Rasterio 的基础重投影 API；不引入 GDAL CLI、完整驱动配置或复杂格式兼容层。
- 实现光学水体工具：指数/阈值、形态学处理、掩膜输出。
- 实现 SAR 水体工具：去斑、阈值、形态学处理、掩膜输出。
- 实现通用后处理：去小斑块、孔洞填充、栅格转矢量。
- 实现面积、数量、覆盖率统计，以及几何有效性和面积异常质检。

**验收标准**：至少 4 个真实案例可输出 GeoTIFF 掩膜、GeoJSON、统计 JSON 和可读报告草稿。

## Phase 2：受约束的 LLM Planner 与工具路由（第 3 周）

**目标**：使 LLM 只负责阶段内的工具匹配和参数规划。

- 为每个工具登记可机读能力、约束、输入输出和回退工具。
- 构建紧凑上下文摘要，禁止传入原始影像或像素数组。
- 用 JSON Schema/Pydantic 验证 Planner 输出；非法计划自动修复一次，仍失败则回退至规则路由。
- 在预处理、核心解译、后处理和质检四个阶段各接入一个受约束规划点。
- 实现规则路由 baseline，以便评估 LLM 路由是否带来收益。

**验收标准**：Planner 对光学和 SAR 案例均能产生合法计划；无法执行的计划不会直接调用工具。

## Phase 3：人工介入、记忆与可观测性（第 4 周）

**目标**：完成“可控、可审计”的 Agent 体验。

- 实现人工审批队列与恢复 API/CLI：批准、编辑参数、拒绝并要求重规划。
- Trace 记录：状态迁移、LLM 输入摘要、计划、工具参数、耗时、错误、人工决策与 artifact URI。
- 记忆分层：
  - 任务记忆：当前 job 的 checkpoint 和摘要；
  - 经验记忆：同传感器/任务的有效参数范围、常见失败和人工偏好；
  - 禁止把原始影像、完整 trace 直接写进长期记忆。
- 实现失败注入开关：工具超时、文件缺失、质检失败、非法 Planner 输出。

**验收标准**：可演示一次人工修改阈值后恢复；可按 job 回放完整决策链；至少 4 类失败可恢复或明确转人工。

## Phase 4：数据集、评测与报告（第 5 周）

**目标**：形成可信的演示资产和量化结论。

- 整理不少于 24 个带标注**评测案例**：光学与 SAR 各 12 个，至少覆盖 2～3 档分辨率；不构建训练集，也不训练项目内模型。
- 所有解译能力应来自免训练算法或许可证明确的预训练轻量模型；记录模型名称、版本、权重来源和适用条件。
- 每个案例包含 `manifest.json`、影像、标签、许可/来源、任务类型、预期路由和基准指标。
- 评测案例保持固定、版本化。另准备 2--4 个不计入正式指标的冒烟案例，供开发阶段验证文件读取和工作流；不要针对正式评测集逐案例手工调参。
- 建立评测 Harness，支持基线规则路由与 LLM 路由对比。
- 自动生成评测报告和任务级证据包。

**验收标准**：一条命令批量运行全部评测案例，输出可比较的 CSV/JSON/HTML 报告。

## Phase 5：演示产品与简历材料（第 6 周）

**目标**：把工程能力转化为可展示成果。

- 提供 CLI 和轻量 Web UI：上传/选择案例、查看阶段状态、审批、产物预览和 trace。
- 将 Web UI 作为正式演示入口：支持任务创建、实时阶段状态、人工审批、掩膜/矢量/统计结果浏览和 trace 时间线；CLI 只保留给运维、批量评测与调试。
- 录制两个演示：正常端到端运行；核心工具失败后 checkpoint 恢复并人工干预。
- 完善架构图、数据契约、失败恢复时序图、评测结果和 README。
- 提炼简历表述与可面试讲解的问题清单。

**验收标准**：新用户可在 10 分钟内运行一个示例，并清楚看到工具选择、产物、审批和恢复过程。

## 5. 数据集规范

建议优先引用许可证明确的公开遥感影像与标签；该影像集是**评测集**，不是训练集。仓库只存小型切片和 manifest，大型原始数据使用下载脚本与校验和。模型权重只引用其公开来源或下载脚本，不随仓库提交。

```text
data/
  manifests/
    case_001.json
  raw/                 # 默认忽略，不提交
  labels/              # 默认忽略或仅提交小样例
  samples/             # 可提交的演示小样例
```

每个 manifest 必须包含：数据来源与许可、传感器类别、采集日期、波段说明、CRS、分辨率、空间范围、标签 URI、标签类别、切片来源和哈希。使用预训练模型时，任务运行记录还必须包含模型/权重版本与推理配置。

## 6. 评测设计

### 6.1 遥感结果指标

- 栅格/矢量 IoU、F1、面积误差、对象数量误差。
- 质检召回率：能否识别无效几何、空结果、面积异常、低质量输入。

### 6.2 Agent 工程指标

| 指标 | 含义 |
| --- | --- |
| 端到端任务成功率 | 案例能产生通过质检的完整结果比例。 |
| 路由准确率 | 计划的工具链是否匹配人工标注的预期工具链。 |
| 计划合法率 | Planner 输出能通过 Schema 和工具契约校验的比例。 |
| 故障恢复率 | 注入故障后能自动或经人工处理完成的比例。 |
| 重复计算比例 | 恢复后重复执行已成功步骤的比例，目标接近 0。 |
| 人工介入率 | 自动完成与需要人工介入任务的比例。 |
| 可追溯完整率 | 结果可关联输入、工具版本、参数、trace、checkpoint 的比例。 |
| 成本与时延 | LLM 调用次数、工具耗时、总耗时。 |

## 7. 推荐的演示场景

1. 光学影像水体提取：Agent 识别 NIR 波段存在，选择 NDWI 工具，输出面积和矢量结果。
2. SAR 影像水体提取：Agent 路由到去斑与阈值工具，采用不同参数策略。
3. 故障恢复：在后处理阶段人为抛出超时错误；重启后只重试失败节点。
4. 人工审批：质检发现面积异常，人工编辑阈值，系统从安全 checkpoint 恢复。

## 8. 里程碑决策

- Phase 1 未跑通 PNG/JPEG、光学 GeoTIFF 和 SAR GeoTIFF 的最小读取链路前，不接入 LLM；不配置 GDAL CLI 或全量驱动。
- Phase 2 先采用规则路由 baseline；LLM 不能降低稳定性，失败必须可回退。
- Phase 4 只使用评测影像和预训练模型/免训练算法；不新增训练流程，也不对正式评测案例逐个调参。
- Phase 4 前不扩展第三种影像类型或第三个地物任务。
- 任何新工具先提供契约、样例输入输出、失败分类与测试，再登记到工具库。

## 10. 开发顺序

从 **Phase 0** 开始。首次编码任务应限定为：初始化项目、定义领域模型、完成 SQLite checkpoint 与 mock 五阶段工作流及其恢复测试。完成后再进入真实遥感 I/O。
