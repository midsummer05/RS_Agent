# 受约束的 LLM 路由策略

## 为什么调整

旧实现让 LLM 在预处理、解译、后处理和 QA 四个阶段都可生成计划，并允许它直接修改连续参数。当前项目中光学和 SAR 在每个阶段都只有一个可执行工具，这不是真正的工具路由；模型实际只是在猜 NDWI 阈值或 SAR 分位数。此前完整评测显示这种猜测使平均 IoU 从规则的 0.300853 降至 0.217172。

## 当前策略

1. LLM 只可参与 `interpret` 阶段的**工具分支选择**；预处理、后处理、QA 和报告固定规则执行。
2. Planner 先查询工具注册表。只有存在两个或以上兼容工具时，才请求 LLM。
3. 若只有一个兼容工具，写入 `rule_single_eligible_route` trace，保留确定性默认配置，不发模型请求。
4. 即使未来 LLM 确认默认工具，也锁定默认工具的数值参数；LLM 不能把它变成任意连续阈值。
5. 影像预处理写入不含像素和标签的路由诊断：有效像元比例、NDWI/VV 分位数、有限候选覆盖率。这些仅在未来存在真实工具分支时提供给 LLM。
6. 所有模型计划仍先经 JSON Schema 和工具契约校验；异常或不合法计划回退规则路径。

所以当前“LLM 路由已启用”指规划器具备并使用了这套决策门控，并不意味着每一张图都会强制调用 API。单一路由时调用模型没有信息增益，只增加时延、费用和参数漂移风险。

## 本次验证

优化后完整 24 例对照见 [报告](../evaluation-output/phase4-/20260905T090417.874172Z/evaluation.html) 与 [审计](../evaluation-output/phase4-/20260905T090417.874172Z/audit.json)。两条路径得到相同结果：平均 IoU 0.300853、成功率 83.33%；LLM 路由路径 24/24 次记录为单一路由延迟，模型请求 0。这是预期的、可审计的弃权，不是伪造 API 调用。

## 何时重新调用 LLM

在实现至少两条可实际执行、各自有离线基准和明确适用条件的工具分支后，例如经验证的 SAR Otsu 与自适应阈值分支，或云遮蔽处理与标准 NDWI 分支，才重新开放模型路由。届时应：

- 给每个分支固定参数配置及适用条件；
- 以不含真值的诊断特征作为模型上下文；
- 保留规则默认分支和回退；
- 重新运行 24 例对照，要求 LLM 选择分支的指标不低于默认基线，再推广。
